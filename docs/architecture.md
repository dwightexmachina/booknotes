# Architecture

## Components

```
CLI  (cli/, Dart) ──────────────┐  all writes + reads
                                ▼
                     SQLite  ~/.booknotes/books.db
                                ▲
Browser ◀── booknotes serve (localhost:8080)
            read-only JSON API  +  static Flutter web build (app/build/web)
```

- **CLI** (`cli/bin/booknotes.dart`) — the only write path. Talks to SQLite
  directly via `package:sqlite3` (FFI). Subcommands: `book`, `note`, `serve`,
  `export`.
- **Server** (`booknotes serve`, `cli/lib/src/server.dart`) — a `shelf` HTTP
  server bound to localhost only. Serves the read-only JSON API under `/api/*`
  and the built Flutter web app for every other path. It holds its own SQLite
  connection; the database runs in WAL mode with a 5 s busy timeout, so the
  CLI can write while the server is running, and the server sees committed
  changes immediately (the UI has a refresh button).
- **Web UI** (`app/`, Flutter web) — a read-only viewer. Fetches
  `/api/books` and `/api/books/<id>` from its own origin. It never touches
  SQLite and performs no writes.
- **Static snapshot** (`booknotes export`, `cli/lib/src/export.dart`) — dumps
  the same JSON shapes to `app/assets/data/` so a serverless host can run the
  UI. Builds made with `--dart-define=STATIC_DATA=true` read those assets
  instead of the API; that is how GitHub Pages works
  ([deploy.md](deploy.md)).

## Design decisions

- **Why a server at all**: Flutter web runs in a browser sandbox and cannot
  open a file on disk, so `serve` bridges the SQLite file to the browser.
- **Word counts are computed, never stored** — at read time, by one shared
  rule (see [schema.md](schema.md#word-count-rule)). They cannot drift from
  the note text.
- **Note ordering is explicit** — an integer `position` column maintained by
  the CLI, not a timestamp. See [schema.md](schema.md#ordering-invariants).
- **UUIDs (v4) as primary keys**, generated by the CLI. Commands accept
  unambiguous prefixes so humans never type full UUIDs.

## Repository layout

```
booknotes/
├── cli/                  Dart package: CLI + server (package name "booknotes")
│   ├── bin/booknotes.dart      command definitions & arg parsing
│   └── lib/src/
│       ├── db.dart             path resolution, connection, schema DDL
│       ├── repo.dart           all queries & mutations; word-count rule
│       ├── server.dart         shelf routes + static hosting
│       └── export.dart         static JSON snapshot for GitHub Pages
├── app/                  Flutter web viewer (package name "booknotes_app")
│   ├── lib/                    main.dart, api.dart, models.dart, theme.dart
│   ├── assets/data/            committed snapshot for the Pages build
│   └── build/web/              prebuilt bundle hosted by `booknotes serve`
├── .github/workflows/    deploy.yml — builds & publishes to GitHub Pages
└── docs/                 this documentation (canonical)
```

## Dev mode for the UI

`flutter run -d chrome` serves the app from a random dev port, so same-origin
API calls would miss. Point it at a running server instead:

```sh
cd app && flutter run -d chrome --dart-define=API_BASE=http://localhost:8080
```

API responses send `Access-Control-Allow-Origin: *` to permit this.
